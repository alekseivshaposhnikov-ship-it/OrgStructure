# CR007. Новый единый формат отображения организационной диаграммы

## 1. Цель

Необходимо изменить принцип отображения организационной диаграммы.

Переключатель:

```text
Вертикальная / Горизонтальная
```

больше не нужен.

В приложении должен остаться **один формат отображения организационной структуры**.

Диаграмма должна выглядеть как классическая организационная схема:

1. сверху — выбранное подразделение;
2. ниже — его непосредственные дочерние подразделения, расположенные горизонтально колонками;
3. ниже каждого подразделения — его собственная ветка;
4. подразделения одного управленческого уровня должны быть выровнены по вертикали;
5. сотрудники подразделения отображаются отдельной колонкой внутри ветки этого подразделения;
6. если у подразделения есть дочерние подразделения, они также отображаются отдельными колонками.

---

# 2. Пример ожидаемого результата

Для выбранной:

```text
Дирекция по Информационным технологиям
```

верхним узлом диаграммы должна быть:

```text
ДИРЕКЦИЯ ПО ИНФОРМАЦИОННЫМ ТЕХНОЛОГИЯМ
```

Ниже горизонтально располагаются непосредственные подразделения дирекции:

```text
                 ДИРЕКЦИЯ ПО ИНФОРМАЦИОННЫМ ТЕХНОЛОГИЯМ
                                   │
          ┌────────────────────────┼────────────────────────┐
          │                        │                        │
      ОТДЕЛ A                  ОТДЕЛ B              ПРОЕКТНЫЙ ОФИС
```

Каждое подразделение формирует собственную визуальную колонку/ветку.

---

# 3. Главный принцип: организационная иерархия первична

Основой диаграммы остается **реальная организационная иерархия подразделений**.

Настоящие связи:

```text
parent → child
```

должны сохраняться.

Например:

```text
Дирекция IT
├── Отдел A
│   └── Отдел A1
└── Отдел B
    └── Отдел B1
```

должна отображаться именно как:

```text
                 ДИРЕКЦИЯ IT
                      │
           ┌──────────┴──────────┐
           │                     │
        ОТДЕЛ A               ОТДЕЛ B
           │                     │
        ОТДЕЛ A1              ОТДЕЛ B1
```

Нельзя менять родителя подразделения ради визуального расположения.

Нельзя переносить подразделение в другую ветку только из-за значения `sub_level`.

---

# 4. Роль `sub_level`

`sub_level` используется **не для изменения иерархии**, а для вертикального выравнивания подразделений на диаграмме.

Для подразделения необходимо использовать `sub_level` **руководителя этого подразделения**.

Условно:

```text
department visual level = department.manager.sub_level
```

или соответствующее нормализованное поле внутренней модели:

```text
manager.subLevel
```

Иерархия определяет:

```text
КТО ПОД КЕМ
```

`sub_level` определяет:

```text
НА КАКОЙ ВЫСОТЕ РАСПОЛОЖИТЬ КАРТОЧКУ
```

---

# 5. Выравнивание по `sub_level`

Подразделения с одинаковым `sub_level` руководителя должны находиться на одной горизонтальной линии диаграммы.

Например:

```text
Дирекция IT          sub_level = 2
│
├── Отдел A          sub_level = 3
│   └── Отдел A1     sub_level = 4
│
└── Отдел B          sub_level = 3
    └── Отдел B1     sub_level = 4
```

должно отображаться:

```text
                    ДИРЕКЦИЯ IT
                     level 2
                        │
             ┌──────────┴──────────┐
             │                     │
          ОТДЕЛ A               ОТДЕЛ B
           level 3               level 3
             │                     │
             │                     │
          ОТДЕЛ A1              ОТДЕЛ B1
           level 4               level 4
```

Обязательный инвариант:

```ts
if (A.managerSubLevel === B.managerSubLevel) {
    A.y === B.y;
}
```

При этом `A` и `B` могут относиться к разным веткам.

---

# 6. `sub_level` не изменяет parent-child

Если данные содержат:

```text
Отдел A       sub_level = 3
└── Отдел A1  sub_level = 3
```

совпадение `sub_level` не делает эти подразделения siblings.

Реальная связь:

```text
Отдел A → Отдел A1
```

должна сохраниться.

`sub_level` влияет на вертикальную координату, но **никогда не изменяет `parentId`**.

Если реальные данные содержат необычную комбинацию иерархии и `sub_level`, не пытаться автоматически «исправлять» организационную структуру.

---

# 7. Выбранное подразделение

Подразделение, выбранное пользователем в левом дереве, является верхним узлом текущей диаграммы.

Например пользователь выбирает:

```text
Дирекция по Информационным технологиям
```

Диаграмма начинается именно с:

```text
Дирекция по Информационным технологиям
```

и показывает только ее отображаемую ветку.

Если пользователь выбирает:

```text
Отдел информационной безопасности
```

верхним узлом становится:

```text
Отдел информационной безопасности
```

и отображается его ветка.

Значение `sub_level` выбранного root не должно создавать над ним пустые уровни.

Выбранный root всегда является верхней карточкой текущей визуализации.

---

# 8. Дочерние подразделения

Все непосредственные дочерние подразделения одного родителя должны располагаться горизонтально — отдельными колонками.

Например:

```text
                    ДИРЕКЦИЯ
                        │
       ┌────────────────┼────────────────┐
       │                │                │
    ОТДЕЛ A          ОТДЕЛ B          ОТДЕЛ C
```

Не допускается превращение siblings в длинную последовательную цепочку:

```text
Дирекция
   │
Отдел A
   │
Отдел B
   │
Отдел C
```

если в реальной структуре A, B и C имеют одного родителя.

---

# 9. Вложенные подразделения

Если внутри отдела существуют дочерние подразделения, тот же принцип применяется рекурсивно.

Например:

```text
ОТДЕЛ A
├── ОТДЕЛ A1
├── ОТДЕЛ A2
└── ОТДЕЛ A3
```

должен отображаться как отдельная ветка:

```text
                         ОТДЕЛ A
                            │
             ┌──────────────┼──────────────┐
             │              │              │
          ОТДЕЛ A1       ОТДЕЛ A2       ОТДЕЛ A3
```

Если внутри `A1` существуют свои подразделения:

```text
ОТДЕЛ A1
├── ГРУППА A11
└── ГРУППА A12
```

они снова располагаются колонками внутри ветки `A1`.

Таким образом один и тот же алгоритм применяется рекурсивно на любой глубине структуры.

---

# 10. Визуальная группировка ветвей

Очень важно сохранить визуальную принадлежность элементов своему родителю.

Например:

```text
ROOT
├── A
│   ├── A1
│   └── A2
└── B
    ├── B1
    └── B2
```

должно визуально читаться как две самостоятельные ветки:

```text
                         ROOT
                           │
                ┌──────────┴──────────┐
                │                     │
                A                     B
                │                     │
          ┌─────┴─────┐         ┌─────┴─────┐
          │           │         │           │
          A1          A2        B1          B2
```

Недопустимо визуально перемешивать:

```text
A1, B1, A2, B2
```

только потому, что у них одинаковый `sub_level`.

То есть:

> `sub_level` выравнивает строки, но parent-child определяет горизонтальную группировку.

---

# 11. Сотрудники подразделения

Обычные сотрудники **не являются организационным уровнем**.

Они не участвуют в layout по `sub_level`.

Сотрудники всегда остаются привязаны к своему подразделению.

Если у подразделения нет дочерних подразделений, после его открытия отображается список его сотрудников.

Например:

```text
             ОТДЕЛ A
                │
          СОТРУДНИКИ ОТДЕЛА
                │
          Иван Иванов
          Петр Петров
          Анна Иванова
```

Существующий формат карточек сотрудников сохранить.

---

# 12. Сотрудники при наличии дочерних подразделений

Если подразделение одновременно содержит:

* сотрудников непосредственно этого подразделения;
* дочерние подразделения,

то сотрудники родительского подразделения должны отображаться **в собственной отдельной колонке**.

Например:

```text
                           ОТДЕЛ A
                              │
             ┌────────────────┼────────────────┐
             │                │                │
       СОТРУДНИКИ          ОТДЕЛ A1         ОТДЕЛ A2
        ОТДЕЛА A
             │                │                │
        Иван Иванов       сотрудники       сотрудники
        Петр Петров        отдела A1        отдела A2
        Анна Иванова
```

Таким образом содержимое `Отдела A` состоит из параллельных колонок:

```text
[ сотрудники непосредственно Отдела A ]
[ дочерний Отдел A1 ]
[ дочерний Отдел A2 ]
...
```

Сотрудники дочернего отдела остаются внутри ветки своего дочернего отдела.

---

# 13. Сотрудники не участвуют в `sub_level` layout

`sub_level` сотрудников не должен использоваться для определения строк организационной схемы.

Например:

```text
Отдел A
sub_level руководителя = 3

Иван Иванов
sub_level = 5

Петр Петров
sub_level = 6
```

это **не означает**, что необходимо создавать:

```text
level 3 → Отдел A
level 5 → Иван Иванов
level 6 → Петр Петров
```

Сотрудники являются содержимым колонки своего подразделения.

---

# 14. Руководитель подразделения

Руководитель подразделения продолжает отображаться внутри карточки подразделения согласно существующему дизайну.

Он не должен дополнительно дублироваться в колонке обычных сотрудников.

Именно у руководителя подразделения необходимо получать `sub_level`, используемый для вертикального выравнивания карточки подразделения.

---

# 15. Временный вывод `sub_level` для отладки

На время реализации CR007 необходимо вывести значение `sub_level` руководителя непосредственно в карточке подразделения.

Например:

```text
ОТДЕЛ ИНФОРМАЦИОННОЙ
БЕЗОПАСНОСТИ

Иванов Иван Иванович
Начальник отдела

sub_level: 3.0
```

Это необходимо для визуальной проверки layout.

### Важно

Сейчас `sub_level` в карточках подразделений не выводится.

Для debug-отображения необходимо:

1. определить руководителя подразделения существующим механизмом;
2. получить его `sub_level`;
3. вывести значение в карточке подразделения.

Если внутреннее нормализованное поле называется:

```text
subLevel
```

использовать его.

Если руководитель отсутствует или значение не определено:

```text
sub_level: —
```

Debug-поле не должно влиять на размеры/расчет уровней сильнее, чем необходимо для размещения дополнительной строки текста.

Предпочтительно предусмотреть простой флаг:

```ts
SHOW_SUB_LEVEL_DEBUG = true
```

чтобы после проверки диагностическое поле можно было отключить без изменения алгоритма layout.

---

# 16. Вакансии

Существующую бизнес-логику вакансий не менять.

Вакансия относится к тому подразделению, которому она принадлежит.

Вакансии должны отображаться вместе с сотрудниками соответствующего подразделения согласно существующим правилам приложения.

Вакансии:

* не являются подразделениями;
* не создают новый организационный уровень;
* не участвуют в выравнивании по `sub_level`;
* не влияют на parent-child структуру подразделений.

---

# 17. Административный ассистент

Существующую специальную логику административного ассистента сохранить.

Административный ассистент остается специальным сотрудником рядом с руководителем верхнего выбранного подразделения.

Он:

* не является подразделением;
* не участвует в расчете `sub_level` layout;
* не создает дополнительный уровень;
* не должен попадать в обычную колонку сотрудников второй раз.

---

# 18. Раскрытие подразделений

Сохранить существующую возможность раскрывать/сворачивать содержимое подразделений, если она используется текущей диаграммой.

При раскрытии подразделения отображается его содержимое:

```text
department
    |
    +-- direct employees column
    |
    +-- child department 1
    |
    +-- child department 2
    |
    +-- ...
```

Если прямых сотрудников нет, пустую колонку сотрудников создавать не нужно.

Если дочерних подразделений нет, отображается только колонка сотрудников.

Если нет ни сотрудников, ни дочерних подразделений, подразделение остается конечным узлом.

---

# 19. Один формат диаграммы

Переключатель:

```text
Вертикальная / Горизонтальная
```

необходимо удалить из пользовательского интерфейса.

Не должно существовать двух разных способов построения диаграммы.

После CR007 приложение использует только новый единый формат.

Также необходимо удалить или перестать использовать код, который переключает layout между двумя orientation.

При этом не выполнять ненужный большой рефакторинг приложения.

Если старый layout-код безопаснее оставить неиспользуемым на первом этапе, допустимо оставить его, но он не должен участвовать в runtime-построении новой диаграммы.

---

# 20. AS IS / TO BE / «Изменения»

Новый формат должен одинаково использоваться во всех режимах:

```text
AS IS
TO BE
Изменения
```

Сначала существующая бизнес-логика формирует нужную версию организационной структуры.

Затем единый renderer/layout отображает эту структуру.

Не создавать отдельные алгоритмы:

```text
AsIsLayout
ToBeLayout
ChangesLayout
```

---

# 21. Разделение ответственности layout

При расчете положения подразделения учитывать два независимых фактора.

### Вертикальная координата

Определяется управленческим уровнем:

```text
manager.sub_level
```

### Горизонтальная координата

Определяется:

* реальной parent-child структурой;
* положением ветки;
* sibling order;
* шириной дочернего subtree;
* наличием колонки непосредственных сотрудников.

Условно:

```text
Y = management level
X = hierarchy / branch
```

Это главный принцип нового layout.

---

# 22. Не использовать глобальную группировку только по `sub_level`

Нельзя реализовать алгоритм следующим образом:

```ts
Map<subLevel, Department[]>
```

→ взять все подразделения одного `sub_level`

→ просто расположить их подряд в строке.

Такой подход потеряет визуальную структуру ветвей.

`sub_level` нужен для определения `Y`, но расчет `X` должен учитывать реальную иерархию.

Например:

```text
ROOT
├── A
│   ├── A1
│   └── A2
└── B
    ├── B1
    └── B2
```

при одинаковом `sub_level` у `A1`, `A2`, `B1`, `B2` все четыре карточки действительно имеют одинаковый `Y`.

Но горизонтально они должны оставаться сгруппированы:

```text
A1 A2          B1 B2
─────          ─────
ветка A        ветка B
```

а не перемешиваться.

---

# 23. Рекомендуемый принцип расчета layout

Перед реализацией изучить текущую архитектуру и выбрать минимально инвазивный вариант.

Layout должен работать примерно следующим образом:

### Шаг 1

Получить выбранную отображаемую ветку.

### Шаг 2

Для каждого подразделения один раз определить:

```ts
{
    id,
    parentId,
    manager,
    managerSubLevel,
    directEmployees,
    vacancies,
    children
}
```

### Шаг 3

Определить вертикальные уровни подразделений по `managerSubLevel`.

### Шаг 4

Рекурсивно определить необходимую ширину каждой ветки с учетом:

* дочерних подразделений;
* колонки непосредственных сотрудников.

### Шаг 5

Расположить дочерние подразделения горизонтально внутри диапазона своего родителя.

### Шаг 6

Выровнять карточки одинакового `managerSubLevel` по одинаковой координате `Y`.

### Шаг 7

Построить реальные parent-child connectors.

---

# 24. Что нельзя делать

Необходимо исключить следующие варианты реализации.

### Нельзя строить длинную цепочку

Неверно:

```text
Дирекция
   |
Отдел A
   |
Отдел B
   |
Отдел C
```

если A, B и C являются siblings.

### Нельзя перестраивать hierarchy по `sub_level`

Нельзя менять:

```text
parentId
```

ради выравнивания карточек.

### Нельзя глобально смешивать ветки

Одинаковый `sub_level` не означает, что подразделения можно расположить в произвольном порядке.

### Нельзя считать сотрудников организационными уровнями

Сотрудники всегда являются содержимым подразделения.

### Нельзя сохранять два разных layout

После реализации используется один формат диаграммы.

---

# 25. Ключевой пример для реализации

Исходные данные:

```text
Дирекция IT
sub_level = 2

├── Отдел A
│   sub_level = 3
│
│   ├── сотрудники непосредственно A
│   │
│   ├── Отдел A1
│   │   sub_level = 4
│   │   └── сотрудники A1
│   │
│   └── Отдел A2
│       sub_level = 4
│       └── сотрудники A2
│
└── Отдел B
    sub_level = 3

    ├── сотрудники непосредственно B
    │
    └── Отдел B1
        sub_level = 4
        └── сотрудники B1
```

Ожидаемая логика отображения:

```text
                            ДИРЕКЦИЯ IT
                              level 2
                                 │
                 ┌───────────────┴───────────────┐
                 │                               │
              ОТДЕЛ A                         ОТДЕЛ B
               level 3                         level 3
                 │                               │
       ┌─────────┼─────────┐             ┌───────┴────────┐
       │         │         │             │                │
 сотрудники   ОТДЕЛ A1  ОТДЕЛ A2    сотрудники        ОТДЕЛ B1
  отдела A     level 4   level 4      отдела B          level 4
       │         │         │             │                │
    список    сотрудники сотрудники     список         сотрудники
```

При этом карточки:

```text
Отдел A1
Отдел A2
Отдел B1
```

имеют одинаковый `sub_level` и должны находиться на одной горизонтальной линии.

Но:

```text
A1, A2
```

остаются визуально внутри ветки `A`, а:

```text
B1
```

остается внутри ветки `B`.

# 27. Критерии приемки

* [ ] Переключатель «Вертикальная / Горизонтальная» удален.
* [ ] В приложении используется один формат организационной диаграммы.
* [ ] Выбранное подразделение располагается сверху.
* [ ] Его непосредственные дочерние подразделения располагаются горизонтально колонками.
* [ ] Реальная parent-child иерархия сохранена.
* [ ] Дочерние подразделения каждого отдела остаются внутри его визуальной ветки.
* [ ] Вложенные подразделения также располагаются колонками.
* [ ] `sub_level` берется у руководителя подразделения.
* [ ] Подразделения одинакового `sub_level` выровнены по одной координате Y.
* [ ] `sub_level` не изменяет реальный `parentId`.
* [ ] Ветки с одинаковым `sub_level` не перемешиваются.
* [ ] Непосредственные сотрудники подразделения отображаются отдельной колонкой.
* [ ] Колонка непосредственных сотрудников находится рядом с колонками дочерних подразделений.
* [ ] Сотрудники дочернего подразделения остаются внутри его ветки.
* [ ] Сотрудники не участвуют в layout по `sub_level`.
* [ ] Руководитель не дублируется среди обычных сотрудников.
* [ ] Вакансии работают по существующей логике.
* [ ] Административный ассистент работает по существующей специальной логике.
* [ ] `sub_level` временно отображается в карточках подразделений для отладки.
* [ ] При отсутствии значения отображается `sub_level: —`.
* [ ] AS IS использует новый layout.
* [ ] TO BE использует новый layout.
* [ ] «Изменения» использует новый layout.
* [ ] Сценарные операции продолжают работать.
* [ ] Расчет численности не изменился.

# 28. Перед внесением изменений

Перед написанием кода сначала изучить существующую архитектуру и дать короткий технический анализ:

1. где сейчас формируется flat data диаграммы;
2. как определяется `parentId`;
3. как определяется руководитель подразделения;
4. где хранится нормализованный `sub_level`;
5. как сейчас устроено раскрытие подразделений;
6. как сотрудники добавляются к подразделению;
7. как обрабатываются вакансии;
8. как обрабатывается административный ассистент;
9. какие части текущего renderer/layout можно переиспользовать;
10. какие файлы необходимо изменить;
11. как удалить orientation switch без влияния на бизнес-логику.

После анализа реализовать минимально инвазивное изменение.

Не изменять API-модель и scenario-manager без необходимости.

## Главный принцип CR007

> **Иерархия определяет ветки. `sub_level` руководителя определяет вертикальный уровень. Непосредственные сотрудники являются отдельной колонкой своей ветки. Дочерние подразделения располагаются горизонтально колонками.**
