# CR: Перевод PDF-экспорта организационной структуры на единый Unified Layout

## 1. Цель

Привести экспорт организационной структуры в PDF к той же логике построения схемы, которая используется на экране.

Сейчас экранная диаграмма уже строится через единый:

```js
computeUnifiedLayout()
```

и корректно учитывает:

* реальную `parent-child` иерархию;
* управленческие уровни подразделений;
* `sub_level`;
* `effectiveLayoutLevel`;
* `row`;
* sibling alignment;
* дочерние подразделения;
* отдельные колонки сотрудников;
* вакансии;
* административных ассистентов.

PDF при этом визуально строится по другой схеме.

В результате одна и та же организационная структура на экране и в PDF имеет различную геометрию и воспринимается как две разные оргструктуры.

Необходимо устранить это расхождение.

---

# 2. Главный архитектурный принцип

Экран и PDF должны использовать **один и тот же layout**.

Целевая архитектура:

```text
                  Organization Tree
                         │
                         ▼
                computeUnifiedLayout()
                         │
                  Unified Layout
                         │
              ┌──────────┴──────────┐
              │                     │
              ▼                     ▼
       Screen Renderer         PDF Renderer
              │                     │
              ▼                     ▼
        Interactive SVG          PDF / SVG
```

`computeUnifiedLayout()` является единственным источником:

* координат узлов;
* визуальных строк;
* размеров;
* parent-child связей;
* расположения подразделений;
* расположения employee columns.

PDF renderer не должен самостоятельно заново строить организационный layout.

---

# 3. Что должно совпадать между экраном и PDF

Для одинаковых:

```text
selected root
viewMode
showVacancies
card design / размеры карточек
```

экран и PDF должны использовать одинаковую структурную модель.

Должны совпадать:

```text
department nodes
employee columns
assistant nodes
parent-child relations
effectiveLayoutLevel
row
relative X
relative Y
edges
subtree grouping
```

Иными словами:

> Если две карточки находятся на одной строке на экране, они должны находиться на одной строке в PDF.

Если подразделение является дочерним для другого подразделения на экране, та же связь должна сохраняться в PDF.

---

# 4. Что может отличаться

PDF не обязан быть пиксель-в-пиксель копией viewport экрана.

Допускается адаптация:

* общего масштаба;
* размеров страницы;
* margins;
* служебного заголовка;
* даты;
* размера шрифта при необходимости;
* толщины линий;
* технических параметров SVG/PDF.

Но адаптация к PDF не должна менять организационную геометрию.

Недопустимо ради размещения на странице:

```text
переставлять подразделения между row;
менять parent-child;
превращать employee columns в уровни дерева;
перестраивать subtree;
повторно рассчитывать hierarchy.
```

---

# 5. Удалить дублирующий PDF layout

Перед реализацией найти текущий код PDF-экспорта и определить, где PDF самостоятельно рассчитывает:

```text
x
y
row
level
parentId
children
subtree width
```

или преобразует организационное дерево в отдельную layout-модель.

Эта логика больше не должна использоваться для построения организационной геометрии PDF.

Необходимо использовать результат:

```js
const layout = computeUnifiedLayout(rootNode, options);
```

Конкретный вызов привести к существующей архитектуре проекта.

Не создавать:

```js
computePdfLayout()
buildPdfTree()
calculatePdfLevels()
```

если они повторяют функции `computeUnifiedLayout()`.

---

# 6. Единый результат layout

PDF renderer должен получать уже рассчитанный объект примерно следующего смысла:

```js
{
  width,
  height,
  nodes,
  edges,
  flatData
}
```

и заниматься только его визуализацией.

Для каждого node уже должны быть известны:

```js
node.x
node.y
node.width
node.height
node.type
node.row
node.data
```

PDF renderer не должен повторно вычислять эти значения из `sub_level` или hierarchy.

---

# 7. Подразделения

Для:

```js
NODE_DEPARTMENT
```

использовать координаты из Unified Layout:

```js
node.x
node.y
node.width
node.height
```

Не рассчитывать положение department-card повторно.

Например, если Unified Layout вернул:

```text
Дирекция IT              row 0

1С                       row 1
Web                      row 1
Москва                   row 1
Инфраструктура           row 1
Цифровые платформы       row 1
Проектный офис           row 1
```

PDF обязан сохранить эту структуру.

---

# 8. `sub_level`

PDF не должен иметь собственной логики интерпретации:

```text
sub_level
managerSubLevel
normalizedManagementLevel
effectiveLayoutLevel
```

Все эти решения уже принимаются Unified Layout.

В частности PDF не должен самостоятельно делать:

```js
Math.floor(subLevel)
```

или:

```js
parentLevel + 1
```

или sibling fallback.

PDF получает уже рассчитанный:

```js
row
x
y
```

и использует его.

---

# 9. Сотрудники

Это особенно важно.

Сотрудники не должны превращаться в самостоятельные организационные уровни.

Если Unified Layout представляет сотрудников подразделения через:

```js
NODE_EMPLOYEES
```

PDF должен сохранить эту модель.

То есть:

```text
Отдел
│
├── employee column
│     employee
│     employee
│     employee
│
└── child department
```

не должен превращаться в:

```text
Отдел
   │
employee
   │
employee
   │
employee
```

Сотрудники являются содержимым employee column, а не следующими уровнями организационной hierarchy.

---

# 10. Employee column

Для:

```js
NODE_EMPLOYEES
```

PDF renderer должен использовать:

```js
node.x
node.y
node.width
node.height
node.persons
```

из Unified Layout.

Внутреннее расположение persons должно соответствовать экранному варианту.

Если на экране сотрудники одного подразделения представлены вертикальным списком внутри общей колонки:

```text
┌──────────────────────────┐
│ СОТРУДНИКИ ПОДРАЗДЕЛЕНИЯ │
├──────────────────────────┤
│ Иванов                   │
├──────────────────────────┤
│ Петров                   │
├──────────────────────────┤
│ Сидоров                  │
└──────────────────────────┘
```

PDF должен сохранять ту же концепцию.

---

# 11. Дочерние подразделения и сотрудники

Подразделение может одновременно иметь:

```text
own employees
child departments
```

Например:

```text
Отдел веб-разработки
│
├── сотрудники отдела
│
└── Группа цифрового дизайна
      │
      └── сотрудники группы
```

PDF должен воспроизводить именно эту структуру.

Наличие employee column не должно изменять organizational row дочернего подразделения.

---

# 12. Административный ассистент

Сохранить текущую поддержку:

```js
NODE_ASSISTANT
```

Если Unified Layout определяет положение ассистента, PDF использует готовые координаты.

Не создавать отдельную PDF-логику позиционирования ассистента.

---

# 13. Вакансии

Состояние:

```js
showVacancies
```

должно передаваться в Unified Layout тем же образом, что и для экрана.

При:

```js
showVacancies = true
```

PDF содержит вакансии.

При:

```js
showVacancies = false
```

PDF их не содержит.

Вакансии не должны влиять на hierarchy иначе, чем это уже реализовано в Unified Layout.

---

# 14. «Выгружать PDF без фамилий»

Существующую настройку:

```text
Выгружать PDF без фамилий
```

сохранить.

Она должна влиять только на содержимое карточек PDF.

Она не должна запускать другой layout.

То есть:

```text
PDF с фамилиями
PDF без фамилий
```

используют одинаковые:

```text
nodes
edges
x
y
row
```

если размеры карточок остаются теми же.

---

# 15. Режимы моделирования

PDF должен корректно работать для существующих режимов:

```text
AS IS
TO BE
Изменения
```

Использовать ту же подготовленную структуру, которая передается экранному Unified Layout.

Не создавать отдельную PDF-версию сценария.

---

# 16. Дизайн карточек

Экспорт должен учитывать выбранный пользователем дизайн карточек в той мере, в которой это предусмотрено текущей архитектурой.

Но необходимо разделять:

```text
layout
```

и:

```text
card rendering
```

Layout определяет:

```text
где находится карточка;
какого она размера;
с какими узлами связана.
```

Renderer определяет:

```text
как карточка выглядит.
```

Изменение дизайна карточки не должно переключать PDF на другой алгоритм организационной схемы.

---

# 17. Ширина карточек

Если пользователь изменил:

```text
Ширина карточек
```

и это значение используется экранным Unified Layout, PDF должен использовать соответствующую конфигурацию Unified Layout.

Не должно быть ситуации:

```text
Screen departmentWidth = 350
PDF departmentWidth = hardcoded 220
```

если это приводит к построению другой геометрии.

---

# 18. Compact A4

`Compact A4` также должен использовать:

```js
computeUnifiedLayout()
```

Если для Compact A4 применяются другие размеры:

```text
DEPT_W
DEPT_H
PERSON_W
PERSON_H
colGap
rowGap
```

это допустимо.

Но алгоритм hierarchy/layout остается единым.

То есть:

```text
обычный экран
Compact A4
PDF
```

могут иметь разные размеры карточек, но не разные правила построения оргструктуры.

---

# 19. PDF page fitting

После получения:

```js
layout.width
layout.height
```

PDF должен рассчитать только масштаб размещения готовой схемы на странице.

Концептуально:

```js
const availableWidth = pageWidth - marginLeft - marginRight;
const availableHeight = pageHeight - headerHeight - marginTop - marginBottom;

const pdfScale = Math.min(
  availableWidth / layout.width,
  availableHeight / layout.height
);
```

Затем весь layout масштабируется единым коэффициентом.

Важно:

> Не перестраивать layout ради помещения на страницу.

---

# 20. Сохранять aspect ratio

При масштабировании использовать один коэффициент:

```js
scale
```

для X и Y.

Недопустимо:

```js
scaleX !== scaleY
```

если это визуально деформирует диаграмму.

Карточки и расстояния должны сохранять пропорции.

---

# 21. Центрирование

После определения масштаба центрировать готовую схему относительно доступной области PDF.

Концептуально:

```js
offsetX =
  marginLeft +
  (availableWidth - layout.width * scale) / 2;

offsetY =
  headerHeight +
  marginTop +
  (availableHeight - layout.height * scale) / 2;
```

Это изменение координат всей схемы целиком.

Не изменять относительные координаты отдельных nodes.

---

# 22. Заголовок PDF

Существующий header PDF сохранить:

```text
Организационная структура

Дирекция по информационным технологиям

Целевая структура / Текущая структура / Изменения

дата
```

Header находится вне Unified Layout.

Схема должна начинаться ниже header.

Header не должен участвовать в расчете organizational rows.

---

# 23. Большие структуры

Если структура очень большая, сначала использовать существующую концепцию экспорта на одну страницу с масштабированием.

То есть:

```text
layout
   ↓
uniform scale
   ↓
fit into PDF page
```

Не пытаться в рамках этого CR автоматически разбивать организационную структуру на несколько страниц, если такой функциональности сейчас нет.

Multi-page PDF считать отдельной задачей.

---

# 24. Качество PDF

Не растрировать всю организационную диаграмму в screenshot низкого разрешения.

Предпочтительно сохранить SVG/vector rendering там, где это поддерживает текущая реализация.

Текст и линии должны оставаться читаемыми при увеличении PDF.

Если текущий PDF renderer уже строит SVG, сохранить этот подход.

---

# 25. Connector lines

Линии PDF должны строиться на основе:

```js
layout.edges
```

а не путем повторного анализа `parentId`.

Если Unified Layout возвращает:

```js
edge.parent
edge.child
```

PDF renderer использует именно эти связи.

Connector может иметь отдельную SVG-функцию построения path, но она работает с готовыми координатами nodes.

Например:

```text
parent bottom center
        ↓
horizontal junction
        ↓
child top center
```

Линии не должны влиять на расположение nodes.

---

# 26. Collapse / expand

PDF должен экспортировать текущее ожидаемое состояние структуры согласно существующему поведению приложения.

Если сейчас PDF всегда экспортирует полностью раскрытую выбранную ветку — сохранить это поведение.

Если PDF должен учитывать `collapsedIds`, использовать их при вызове Unified Layout.

Не создавать отдельный механизм collapse внутри PDF renderer.

---

# 27. Debug-поля

Текущий экранный debug:

```text
sub
layout
row
```

предназначен для разработки.

По умолчанию он **не должен попадать в пользовательский PDF**.

Однако на время разработки PDF-export полезно добавить отдельный временный флаг:

```js
SHOW_PDF_LAYOUT_DEBUG = false
```

При его включении можно выводить:

```text
row
effectiveLayoutLevel
```

для диагностики.

В production/export по умолчанию:

```js
SHOW_PDF_LAYOUT_DEBUG = false
```

---

# 28. Не копировать Screen DOM

Не решать задачу путем создания screenshot текущего viewport.

PDF должен строиться из данных Unified Layout.

Не использовать текущий zoom transform экрана:

```text
scale
translateX
translateY
```

как основу PDF.

Например пользователь может находиться на экране при:

```text
zoom = 250%
```

или сместить схему pan-ом.

Это не должно влиять на PDF.

PDF использует:

```text
clean unified layout
+
собственный page-fit scale
```

---

# 29. Ожидаемый кейс — Дирекция IT

Для текущей структуры:

```text
Дирекция по информационным технологиям
```

непосредственные подразделения:

```text
Отдел 1С программирования
Отдел веб-разработки
Отдел информационных технологий в г. Москве
Отдел инфраструктурных решений
Отдел развития цифровых платформ
Проектный офис
```

на экране находятся на одном organizational row.

В PDF они также должны находиться на одной горизонтальной линии.

То есть условно:

```text
                       Дирекция IT
                            |
  ---------------------------------------------------------
  |        |        |          |          |               |
  1С      Web     Москва     Инфра     Цифровые      Проектный
                                      платформы        офис
```

Далее каждая ветка развивается независимо.

Например:

```text
1С
├── сотрудники 1С
└── Группа технической поддержки 1С
    └── сотрудники группы
```

и:

```text
Web
├── сотрудники Web
└── Группа цифрового дизайна
    └── сотрудники группы
```

PDF должен сохранить эту структуру.

```js
const layout = computeUnifiedLayout(root, options);
```

Необходимо защитить от повторного появления отдельной PDF hierarchy logic.

# 34. Не менять в рамках CR

Не менять:

* алгоритм `computeUnifiedLayout()`;
* текущие правила `sub_level`;
* `normalizedManagementLevel`;
* sibling fallback;
* `effectiveLayoutLevel`;
* visual row algorithm;
* X-layout;
* screen renderer;
* screen zoom/pan;
* API;
* организационные данные;
* логику сценариев;
* логику вакансий;
* административного ассистента.

Если при реализации обнаружится проблема непосредственно в `computeUnifiedLayout()`, не исправлять ее скрытно внутри PDF.

Зафиксировать отдельно.

# 35. Минимально инвазивная реализация

Перед изменениями изучить текущий PDF pipeline.

Сначала определить:

1. где начинается обработчик кнопки `Экспорт в PDF`;
2. где сейчас подготавливаются данные для PDF;
3. какой модуль рассчитывает координаты PDF;
4. какой модуль рисует карточки;
5. какой модуль рисует connector lines;
6. где рассчитывается PDF scale;
7. используется ли сейчас `computeUnifiedLayout()` хотя бы частично.

После анализа предложить минимальный путь миграции.

Предпочтительный вариант:

```text
exportPdf()
    ↓
prepare selected tree
    ↓
computeUnifiedLayout(root, layoutOptions)
    ↓
renderUnifiedLayoutToPdf(layout, pdfOptions)
    ↓
save PDF
```

# 36. Разделить Layout и Renderer

Целевая ответственность модулей:

### `unified-layout.js`

Отвечает за:

```text
hierarchy
effective levels
rows
x/y
width/height
nodes
edges
```

### Screen renderer

Отвечает за:

```text
screen SVG
HTML cards
zoom
pan
interaction
collapse buttons
```

### PDF renderer

Отвечает за:

```text
PDF page
header
scale
offset
SVG/PDF cards
lines
text
save
```

PDF renderer **не отвечает за организационную геометрию**.

---

# 37. Не создавать второй Unified Layout

Не копировать функции из:

```js
unified-layout.js
```

в PDF-модуль.

Не создавать аналоги:

```js
resolvePdfEffectiveLevel()
assignPdfRows()
computePdfSubtreeWidth()
positionPdfDepartments()
```

Это снова приведет к расхождению двух реализаций.

Если PDF требуется информация, которой сейчас нет в результате `computeUnifiedLayout()`, сначала оценить возможность добавить нейтральное metadata в результат Unified Layout, пригодное и для других renderer.

# 38. Критерии приемки

CR считается выполненным, если:

* [ ] PDF использует `computeUnifiedLayout()`;
* [ ] экран и PDF больше не имеют двух независимых алгоритмов organizational layout;
* [ ] непосредственные siblings, находящиеся на одной строке экрана, находятся на одной строке PDF;
* [ ] `sub_level 4.0` и `4.1` не интерпретируются PDF повторно;
* [ ] sibling fallback не реализован повторно в PDF;
* [ ] employee columns сохраняются как employee columns;
* [ ] сотрудники не превращаются в уровни дерева;
* [ ] дочерние подразделения остаются под своими реальными parent;
* [ ] административный ассистент отображается корректно;
* [ ] вакансии отображаются в соответствии с `showVacancies`;
* [ ] режим «PDF без фамилий» работает;
* [ ] AS IS / TO BE / Изменения работают;
* [ ] PDF масштабирует готовый layout целиком;
* [ ] aspect ratio сохраняется;
* [ ] схема центрируется на странице;
* [ ] screen zoom/pan не влияет на PDF;
* [ ] PDF header сохраняется;
* [ ] существующий screen renderer не изменен;
* [ ] существующий `computeUnifiedLayout()` не дублируется;
* [ ] добавлены regression tests;
* [ ] `npm test` проходит;
* [ ] `npm run build` проходит.

# 39. Финальная проверка на реальных данных

После реализации выполнить экспорт:

```text
Дирекция по информационным технологиям
```

и сравнить его с экраном.

Особенно проверить шесть непосредственных подразделений:

```text
Отдел 1С программирования
Отдел веб-разработки
Отдел информационных технологий в г. Москве

Отдел развития цифровых платформ
Проектный офис
```

Если на экране они находятся на одной горизонтальной линии, PDF должен сохранить это расположение.

Также проверить дочерние ветки:

```text
Группа технической поддержки 1С
Группа цифрового дизайна
Группа технической поддержки
```

Они должны оставаться под соответствующими родительскими подразделениями, а не менять структуру из-за особенностей PDF renderer.

# Главный принцип CR

> **Экран и PDF — это два renderer одной и той же организационной схемы, а не две разные реализации layout.**

`computeUnifiedLayout()` должен быть единственным источником организационной геометрии.

PDF получает готовые:

```text
nodes
edges
x
y
width
height
row
```

и только отрисовывает их на странице с единым масштабированием.

Если после реализации структура PDF отличается от экранной структурно, даже если PDF выглядит аккуратно, задача считается невыполненной.
